# 后端界面作为唯一基线的双工作区同步规格

日期：2026-09-11

## 目标

以“茶文化智能体后端开发 (2)”工作区的代码、管理后台界面和 Git 历史为唯一基线，覆盖“茶文化智能体前端开发 (2)”工作区以及远程 `main`。同步结束后，两个任务读取到相同的仓库内容和同一个基线提交，登录页与管理工作台不再保留前端任务中的另一套实现。

## 已确认状态

- 后端工作区：`C:\Users\17477\.codex\worktrees\b2de\茶文化智能体`
- 后端分支：`codex/tea-backend-integration`
- 已验证后端基线：`6a1bd38b33f3cf267ea290ef9eba22a73310bf1e`
- 前端工作区：`C:\Users\17477\.codex\worktrees\c604\茶文化智能体`
- 前端旧基线：`172103d134d8470af2de1ae2692c2342e2e53319`
- 前端工作区当前为 detached HEAD，且无未提交修改。
- 远程 `main` 当前指向前端旧基线。
- 两条历史从共同提交 `75151b2` 后各自前进 8 个提交，不能通过快进完成同步。

## 采用方案

采用“归档后定向覆盖”：先保存旧前端主线，再使用 `--force-with-lease` 将远程 `main` 精确更新为后端基线。相比直接删除旧历史，这一方案既满足以后端历史覆盖主线的要求，也保留明确的恢复入口。

不采用普通 merge：它会同时保留两套互相冲突的前端实现，不能保证后台界面以当前后端任务为准。

不采用只复制文件：它只能同步当前文件，不能同步 Git 历史，也会让两个任务继续停留在不同提交上。

## 执行顺序

1. 再次确认两个工作区均无未提交修改，并确认 `main` 仍指向 `172103d`，防止覆盖执行期间误吞新的远程提交。
2. 创建并推送归档分支 `archive/frontend-before-backend-sync-20260911`，精确指向 `172103d`。
3. 将本规格及后续实施计划作为后端基线的文档快照提交，并推送 `codex/tea-backend-integration`。
4. 使用带精确 lease 的强制推送，把远程 `main` 更新到最终后端基线提交。若远程 `main` 已发生变化，操作必须失败并停止，不自动覆盖未知提交。
5. 将前端工作区切换为最终后端基线的 detached HEAD，使两个工作区文件完全一致；后端工作区继续保留在 `codex/tea-backend-integration` 分支上。
6. 在两个工作区分别验证提交哈希、工作区清洁状态和关键文件哈希；在后端工作区运行构建与必要测试。
7. 向“茶文化智能体前端开发 (2)”任务发送同步说明，明确以后端界面为唯一基线，后续改动从新的 `main` 开始。

## Git 与回滚边界

- 覆盖目标仅为远程 `main` 和前端任务的 detached 工作区，不删除 `codex/tea-backend-integration`。
- 旧前端历史保留在远程归档分支中，不删除、不压缩已有提交。
- 强制更新必须使用 `--force-with-lease`，禁止无 lease 的 `--force`。
- 回滚时可将 `main` 恢复到归档分支，或把前端工作区重新切回 `172103d`。

## 验收标准

- 远程 `main` 与 `codex/tea-backend-integration` 指向同一最终提交。
- 两个工作区的 `HEAD` 指向同一最终提交，且 `git status --short` 均为空。
- 两个工作区的登录页、管理后台入口和前端关键源文件哈希一致。
- 后端测试、API 模式前端生产构建和健康检查通过。
- 原前端历史可从 `origin/archive/frontend-before-backend-sync-20260911` 访问。
- 前端任务收到新的基线说明，不再继续沿用旧的 `172103d` 工作树。
