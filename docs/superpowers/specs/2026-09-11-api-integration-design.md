# 茶序前端接口联调架构设计

日期：2026-09-11  
状态：已获聊天确认，待书面规格复核

## 目标

将当前 React/Vite 交互原型演进为可持续维护、可响应式运行、可与后端直接联调的前端。页面体验和已验收业务规则保持不变：七幕 Sticky 首页、问茶与冲泡融合、四套后台职能平台、商品上下架及来源有效性联动仍是交付基线。

本轮不实现服务端、真实身份系统、真实大模型、支付、库存、会员、文件直传或未在接口契约中定义的新业务。

## 现状与设计依据

- 前端为 React 19、TypeScript、Vite；当前业务状态集中在应用内演示数据和 state setter。
- 根目录《茶文化智能体_前后端接口契约与Skill清单.md》是请求、响应、权限与状态迁移的唯一契约依据。
- Figma 主文件已保存桌面与移动端页面捕获；本次读取设计上下文时受 Starter MCP 调用上限限制。按仓库既定策略，沿用已保存的 Figma 状态、截图和 Penpot 备用画布作为视觉基线，不在本轮改动画布。

## 架构

```text
页面 / 可复用 UI
        │  视图模型、加载/错误/空/无权状态
        ▼
功能 hooks 与应用状态边界
        │
        ▼
领域服务（公开检索、问答、咨询、后台内容、审核、线索）
        │  严格请求与响应类型
        ▼
API 适配器 ────────── Runtime mode ────────── Mock 适配器
        │                    │                    │
        ▼                    ▼                    ▼
   /api/v1 HTTP 后端       demo / live         当前本机演示数据
```

页面只能调用领域服务或功能 hooks；不能再读取或改写散落的本地数组。`ApiClient` 负责 URL、cookie、请求信封、响应解析和基础协议头；业务适配器负责契约端点的请求参数、响应类型与规则。Demo 和 live 适配器共享同一接口，运行模式只在应用启动时确定，不在业务组件中分支。

## 协议、类型与运行模式

1. 用 TypeScript 定义 API 信封：成功为 `{ data, meta }`，失败为 `{ error, meta }`，并保留 `request_id` 以便报障。禁止使用 `any` 代替契约字段。
2. `ApiError` 归一化 HTTP 状态、错误码、用户信息、字段细节和 `Retry-After`。页面按 `error.code` 分支，不按中文文案分支。
3. 以 `VITE_API_MODE=mock|live` 和可选 `VITE_API_BASE_URL` 控制运行模式；默认 mock。live 模式使用同域 `/api/v1`，`credentials: 'include'`，不将会话或 CSRF token 写入 localStorage。
4. 所有公开写请求（问答、咨询、反馈、事件）与后台命令请求生成 UUID `Idempotency-Key`。需并发保护的后台 PATCH、审核迁移、下架、重新上架、删除、线索跟进和账户更新携带后端提供的 ETag 到 `If-Match`。
5. 后台写入前取得或刷新 `/admin/auth/csrf`，使用 `X-CSRF-Token`；401 使本地后台身份失效并回到登录/无会话状态，403 只展示无权提示，不伪装为数据为空。

## 数据边界与领域服务

### 公开用户端

- U01 配置决定 `data_mode`、类目、问答能力以及咨询和健康提示文本；页面醒目展示 demo/live 状态。
- U02/U04/U05 负责检索、列表、茶品与批次详情。Tea ID 与 TeaItem ID 严格区分；`tea_item_id` 只能在归属正确时传给 U06/U07/U08。
- U06、U07、U08、U09 显示功效、冲泡、货源和来源；货源空列表仅显示后端 `availability_notice`，不渲染过期价格。
- U11 问答以单次请求呈现；仅当返回 `intent=brewing` 和有效 `tea_item_id` 时，继续通过 U07 载入冲泡步骤。`unconfirmed` 是 200 业务结果；`CONTENT_UNAVAILABLE` 是需刷新公开数据的冲突结果。
- U12 在提交前显示配置下发的用途同意文本和版本，未勾选同意不发请求。成功后只显示脱敏回执字段，不回显完整联系信息。
- U13/U14 保持匿名反馈和白名单事件；失败不阻塞主阅读流程。

### 后台

- A01--A04 构成后台会话边界；`AdminUser.permission_codes` 和 `review_domains` 是菜单与操作入口的唯一前端权限来源，但每次后端请求仍是最终裁决。
- C01--C13 对应内容浏览、草稿、新版、提交审核、审核发布、下架、重新上架与逻辑删除。状态机固定为 `draft → pending_review → published → withdrawn → published`；拒绝返回可编辑 draft。重新上架不增加版本、不重新审核，并以 API 返回为准刷新公开缓存。
- R 不能审核自己修改的版本；A 不因管理员身份获得专家审核权限；O 删除仅限未提交草稿；L 没有内容与发布入口。
- 线索、导入、账号、统计和审计服务只暴露给契约授权的页面。没有正式后端支持的演示操作留在 mock 适配器，live 模式不伪造成功。

## UI 状态与可访问性

每个远程视图有明确的初始加载、后台刷新、空集、字段校验、无会话、无权、版本冲突、限流、服务不可用和未知失败状态。可重试操作保留原上下文；429 呈现后端重试时间；409/428 指引刷新内容再重试；503 不显示为“资料不足”。

现有七幕桌面 Sticky 模型和移动端文档流/邻近吸附不改变。滚动场景只消费公开茶品派生的品类数量，不改变滚动位置。继续满足 `prefers-reduced-motion`、语义 section、焦点管理、键盘操作、自定义批次选择和无横向溢出要求。

## Mock 行为

Mock 适配器迁移现有演示数据及其状态转移：发布且来源有效的数据才对公开端可读；撤回来源后，茶品、问答匹配、冲泡和货源均不可公开；下架后旧详情不可读；重新上架沿用已审核版本且恢复本次演示撤回来源的可用性。Mock 必须返回与 live 适配器一致的类型、分页结构、HTTP/业务错误和 row version 语义，以便页面不依赖模式差异。

## 验收

1. `npm run build` 通过且不存在 TypeScript 漏洞式 `any` 或未使用的模拟直连。
2. Mock 模式下复验七幕首页、搜索、批次详情、问茶自动带入冲泡、咨询同意、四后台角色、审核自动发布、上下架、来源撤回和重新上架。
3. Live 模式以可配置基础地址发送正确路径、snake_case 参数、cookie、幂等键、CSRF 与 `If-Match`；在无后端时显示可理解的服务不可用状态。
4. 浏览器在 1440×900 和 390×844 下复验关键流程、无横向溢出，控制台无 error/warn。
5. README、原型说明、验收记录和 VERSION_SNAPSHOTS.md 与最终行为和快照一致；代码快照经构建和浏览器验收后提交、推送。

## 文件边界

- `prototype/src/api/`：协议类型、HTTP 客户端、错误归一化、运行模式及 mock/live 适配器。
- `prototype/src/features/`：按公开浏览、问答冲泡、咨询、后台认证、内容、审核、线索分隔的服务和 hooks。
- `prototype/src/model.ts`：仅保留共享展示模型与转换边界；演示源数据移入 mock。
- `prototype/src/main.tsx`、`PublicPages.tsx`、`AdminPages.tsx`、`ScrollStory.tsx`：消费功能状态，保留既有路由与交互。
- `prototype/src/ui.tsx`、`styles.css`：复用状态提示与响应式样式，不新增图标依赖。
